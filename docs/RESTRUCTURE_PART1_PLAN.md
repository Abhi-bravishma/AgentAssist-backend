# Restructure Part 1 — Prompt & Config Registry

**Status:** planned, not started
**Branch:** `restructure/part1-config-registry`
**Scope:** Part 1 of a 5-part restructure of the agent-assist backend.

## Where Part 1 sits

| Part | Scope | Status |
|---|---|---|
| **1** | **Prompt & config registry — this document** | **planned** |
| 2 | Split `BaseAiProvider` into separate classes; classifier reads intents from `aa_intent` | not started |
| 3 | Pipeline/stage refactor of `ConversationProcessingService` | not started |
| 4 | Merge the RAG service | not started |
| 5 | Admin portal UI | not started |

Part 1 lays the data layer every later part depends on. The provider switch and
language registry land here as data plus services; the UI that drives them is Part 5.

---

## 1. Goal

Move every hardcoded prompt, checklist, intent definition, brand value and language
name out of Java and into a database-backed, versioned config registry, so that:

- prompt tuning is a data change, not a rebuild and redeploy;
- the active LLM provider (OpenAI or Ollama) can be switched from the admin portal
  at runtime, with no restart;
- language handling is driven by a table rather than by switches scattered across
  two services.

Runtime behaviour must not change while the config is being moved. Behaviour changes
are deliberately separated into their own phase with their own tests.

## 2. Current state

### Hardcoded prompts

| Source | Lines | What is inline |

| `com.agentassist.ai.BaseAiProvider` | 1,454 | 13 prompt text blocks: analysis (x3), translation (x2), language detection, intent classification, sentiment, regeneration (x2), follow-up, compliance, single-text analysis |

Roughly 2,600 lines, most of it prose.

### Provider wiring

`OpenAiProvider` and `OllamaProvider` carry mutually exclusive
`@ConditionalOnProperty(name = "ai.provider", …)`, so exactly one `AiProvider` bean
exists per boot. Four services inject the singular type: `AnalysisService`,
`ChecklistService`, `ComplianceService`, `LanguageService`. Switching provider today
requires an environment change and a restart.

Both Spring AI starters (`spring-ai-openai-spring-boot-starter`,
`spring-ai-ollama-spring-boot-starter`) are already on the classpath — no dependency
work needed.

### Language handling

Three LLM calls minimum per customer turn: detect → translate-to-English → one
translate-from-English per suggestion. Language names are resolved by a 4-case switch
(`describeLanguage`) that special-cases only Chinese.

## 3. Constraints

**Do not modify:** `SecurityConfig`, `CorsConfig`, `RagClient`, `SalesforceClient`,
controller request/response contracts, any DTO.

**Do not change** any prompt wording, including typos and odd spacing. Byte-identical
output is the acceptance criterion for phase 1a.

**Do not delete** any old constant until the golden-prompt tests pass against the
seeded database values.

**Every Liquibase changeset** must define a rollback.

## 4. Audit findings that shape the work

These were found by reading the current source and must be handled explicitly.
Each one silently breaks byte-identity if missed.

### 4.1 `%%` escapes — highest risk

Five prompts in `BaseAiProvider` (lines 157, 272, 610, 726, 938) contain:

```
* current_sentiment_score = 70%% latest message sentiment + 30%% trend
```

`String.formatted()` renders `%%` as a single `%`. The seed must store the **rendered**
form (`70%`), not the source form (`70%%`). Copying the Java text block verbatim
produces a different prompt, and the diff is nearly invisible in a test failure.

The reverse case also exists: `ChecklistService` lines 856, 934 and 1025 contain a
single `%` inside blocks that never go through `.formatted()` — those copy across
unchanged.

### 4.2 Golden fixtures must be captured from rendered output

Copying `FEE_WAIVER_CHECKLIST` is not the same as capturing
`FEE_WAIVER_CHECKLIST.formatted("METROBANK", "Metrobank", "(02) 88-700-700")`.
Fixtures are generated by running the current code, not by hand-copying constants.
This is commit 0, before any schema exists.

### 4.3 Liquibase has never run a migration

`src/main/resources/db/changelog/db.changelog-master.yaml` contains one line —
`databaseChangeLog:` with no entries. Every table today was created by Hibernate
`ddl-auto: update`. Separately, `application.yaml` sets `liquibase.change-log` at the
root instead of `spring.liquibase.change-log`, so that property is inert; it works
only because Liquibase's default path happens to be the same file.

Net effect today is harmless, but the first changeset is the first real exercise of
this wiring. Fix the property key and prove a trivial changeset applies before
building six tables on it.

### 4.4 Deployment target is PostgreSQL, not MySQL

`docker-compose.yml` sets `jdbc:postgresql://localhost:5433/agentassist` with the
PostgreSQL dialect; local dev uses MySQL. `LONGTEXT` is MySQL-only. Use Liquibase's
portable `clob` type throughout — it maps to `LONGTEXT` on MySQL, `TEXT` on
PostgreSQL, `CLOB` on H2, which also makes the H2 test setup work without
compatibility mode.

### 4.5 `ddl-auto: update` will contend with Liquibase

Liquibase runs first, then Hibernate inspects the new entities and may alter what
Liquibase just created. Entity mappings must match the generated DDL exactly, or the
new entities must be excluded from `ddl-auto`. Decide deliberately rather than
discovering column-type drift in production.

### 4.6 `bank_name` has a different fallback from the other brand attributes

```java
resolveBankName:  null/blank → "your bank";  METRO → "Metrobank";
                  SCB → "Standard Chartered";  default → projectName.trim()
resolveHotline:   null/blank → neutral text;  METRO → "(02) 88-700-700";
                  default → neutral text
resolveLoanEmail: null/blank → neutral text;  METRO → "CLOD-ASFD@…";
                  default → neutral text
```

`bank_name` falls back to **the project code itself** for unknown projects; the other
two fall back to a neutral string. A plain "project row → global row → throw"
resolution does not reproduce this. Since `ConversationController` defaults
`projectName` to `HOSPITALITY`, an unseeded project code is the normal case, not an
edge case.

`BrandService` therefore needs: project row → global row → for `bank_name` only, the
project code. This is documented behaviour, not an accident to be cleaned up in this
part.

### 4.7 TELCO has no filtered-intent message

`getFilteredIntentMessage()` has explicit cases for POLICY, CLAIMS, FEE_WAIVER,
HOME_LOAN_CLOSURE and BILLING plus a `default` branch. TELCO falls through to the
default. Seed `aa_intent.filtered_message_template` for TELCO with the default text.

That switch also interpolates the **raw** project code, so with the controller default
the message reads "…through HOSPITALITY…". Byte-identical means leave it.

### 4.8 `NONE` returns an empty checklist

`getChecklistPrompt(OperationType.NONE)` returns `""` today. Short-circuit it — do not
send it to the registry looking for a `checklist.none` key.

### 4.9 `baseLanguage` is written but never read

`ConversationService.getBaseLanguage()` is defined and called by nothing.
`conv.getBaseLanguage()` is read once, only to decide whether to set it. Every
translation uses `detectedLang` from the current message instead. A customer who types
one message in English mid-conversation gets an English-only suggestion for that turn.

The column exists to prevent exactly this. Fixing it is a behaviour change, so it
belongs in phase 1c, not 1a.

### 4.10 Detection failure degrades silently to English

`LanguageService.fromEnglish()` returns the English text unchanged when the tag is
`und`, and `detectLanguage()` returns `und` whenever the model's answer is not a clean
two-letter subtag. The agent receives English with no signal that anything failed.
Also phase 1c.

### 4.11 The model is handed raw language tags

`describeLanguage` special-cases only Chinese; everything else passes the bare tag, so
the prompt reads "Translate strictly to id" rather than "Indonesian". Regional variants
collapse (`pt-BR` → `pt`, `es-MX` → `es`), losing register. The `aa_language` table
fixes this as data.

## 5. Schema

New changelog `db/changelog/changes/part1-config-registry.yaml`, included from the
master changelog. Portable types only (`clob`, not `LONGTEXT`). Every changeset has a
rollback.

### `aa_project`
`id` PK · `code` varchar(50) unique · `display_name` · `active` bool default true ·
`created_at` · `updated_at`

### `aa_brand_attribute`
`id` PK · `project_id` FK → `aa_project`, **nullable** (NULL = global default) ·
`attr_key` varchar(100) · `attr_value` clob · unique(`project_id`, `attr_key`)

### `aa_intent`
`id` PK · `code` varchar(50) unique · `display_name` · `description` clob nullable
(reserved for Part 2 classifier generation) · `active` bool ·
`filtered_message_template` clob nullable, supports `{project}` · `created_at` ·
`updated_at`

### `aa_project_intent`
`id` PK · `project_id` FK · `intent_id` FK · `enabled` bool ·
unique(`project_id`, `intent_id`)

Semantics must match the current switch exactly:

- project has **no rows** → all intents allowed (today's "unknown project → allow all")
- project has rows → only `enabled = true` intents allowed
- `NONE` is always allowed and is never stored
- null or blank project → all intents allowed

### `aa_prompt_template`
`id` PK · `template_key` varchar(100) · `project_id` FK **nullable** (NULL = default) ·
`version` int · `content` clob · `status` varchar(20) `DRAFT|PUBLISHED|ARCHIVED` ·
`created_at` · `created_by` nullable · unique(`template_key`, `project_id`, `version`)

Resolution: highest `PUBLISHED` version for (key, project); if none, highest
`PUBLISHED` version for (key, NULL).

### `aa_language`
`id` PK · `code` varchar(20) unique (`en`, `zh-Hant`, `pt-BR`) · `display_name`
(the phrase given to the model, e.g. "Traditional Chinese (繁體中文), using Traditional
characters only") · `script` nullable · `active` bool · `created_at` · `updated_at`

Replaces `describeLanguage`. The Chinese script-detection character sets stay in Java
for now; moving them is Part 3.

### `aa_setting`
`id` PK · `setting_key` varchar(100) · `project_id` FK **nullable** ·
`setting_value` clob · `updated_at` · `updated_by` nullable ·
unique(`setting_key`, `project_id`)

Part 1 uses exactly one global row: `ai.active_provider` = `OPENAI` | `OLLAMA`.
`project_id` is present for consistency with the other tables and is not used yet.

## 7. Java layer

New package `com.agentassist.configregistry`.

**Entities + Spring Data repositories** for all seven tables, matching the existing
style in `com.agentassist.model`.

**`PromptService`**
- `String render(String templateKey, String projectCode, Map<String,String> vars)` —
  project override, then default; substitutes `{name}`; throws listing every missing
  variable. Extra variables are ignored (brand vars are computed for all checklist
  types today but used by only two).
- `String renderDefault(String templateKey, Map<String,String> vars)`
- 60-second cache, plus `evictAll()` for the portal.

**`BrandService`**
- `String attr(String projectCode, String key)` — project row → global row → for
  `bank_name` only, the project code (§4.6); otherwise throw.

**`IntentRegistryService`**
- `boolean isIntentAllowed(String intentCode, String projectCode)`
- `String filteredMessage(String intentCode, String projectCode)` — renders with
  `{project}`, falling back to `this service` when the project is null
- `List<String> allowedIntents(String projectCode)` — for Part 2

**`LanguageRegistryService`**
- `String describe(String languageCode)` — table lookup, raw tag when absent

**`SettingsService`**
- `String get(String key)` / `void set(String key, String value)`, same cache and
  eviction as `PromptService`

**`RegistryValidator`** — `ApplicationRunner` that checks every expected
`template_key` has a `PUBLISHED` row and logs a table of what it found. Logs ERROR and
continues on failure (some deployments seed later) **and** publishes the result as an
actuator health indicator so a bad deploy can be gated instead of failing at the first
customer message.

### Fail-safety

A missing key or unreachable registry logs ERROR and throws. No silent fallback to an
empty prompt — an empty prompt is worse than an error. Blast radius is the whole
`/process` endpoint, which is why the startup validator and health indicator matter.

## 8. Provider switching

**Decided:** one provider active at a time — never both, never split by task.
Switchable from the admin portal at runtime, no restart.

- Drop the `@ConditionalOnProperty` from both providers so both beans exist.
- Guard construction so the app still starts when only one provider is credentialed
  (a sovereign box has no OpenAI key). `@Autowired(required = false)` with fallback,
  mirroring `ChatClientFactoryImpl` in the bravishma-rag repo — same problem, already
  solved in-house.
- New `AiProviderFactory` reads `ai.active_provider` from `SettingsService` and returns
  the matching bean. The four injection points take the factory instead of the bean.
- Portal writes the setting and evicts the cache; the next request uses the new
  provider.
- If the portal selects a provider that is not available, fail loudly with a clear
  message rather than silently serving the other one.

`ai.provider` in `application.yaml` becomes the bootstrap default used to seed the
setting row; the database is authoritative after that.

## 9. Phasing

Byte-identity is the gate for 1a. The language fixes are genuine behaviour changes, so
they are separated rather than smuggled in.

### Phase 1a — config out of code
Prompts, checklists, brands, intents into the registry.
**Gate:** golden-prompt tests green; every rendered prompt byte-identical to the
captured fixture.

### Phase 1b — plumbing for provider and language
`aa_language`, `aa_setting`, `AiProviderFactory`, `LanguageRegistryService`, portal
switch endpoint. Every setting seeded to today's values.
**Gate:** same provider selected and same output as before. Plumbing lands, behaviour
does not move.

### Phase 1c — behaviour changes, one commit each, each with its own test
1. Wire `baseLanguage` so conversation language is sticky across turns (§4.9)
2. Stop degrading silently to English on `und` (§4.10)
3. Use `aa_language` display names in the translation prompt (§4.11)
4. Collapse `TranslationService` into `LanguageService` — two classes, one job

Each is independently revertible.
